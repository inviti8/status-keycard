# Ed25519 architecture

This applet supports pure Ed25519 (RFC 8032) signing alongside the original secp256k1
functionality, targeted at Stellar (SEP-0005 / SLIP-0010) but not specific to it. This document
describes how it works and why, the wire interface, and what the platform must provide.

## The core idea: no software point arithmetic

JavaCard 3.0.x has no native EdDSA (that arrives in JavaCard 3.1, which shipping cards do not
expose to applets). A byte-oriented software implementation of Edwards curve arithmetic is far too
slow on card CPUs. Instead, `Ed25519.java` uses the same approach as
[dufkan/JCEd25519](https://github.com/dufkan/JCEd25519) and JCMathLib:

1. **Scalar multiplication on the native EC engine.** edwards25519 is birationally equivalent to a
   short-Weierstrass curve ("Wei25519", see RFC 9380 appendix and the JCMathLib constants). Since
   the map preserves the group structure, `s·B` can be computed by the card's hardware EC
   accelerator with custom curve parameters, exactly the way this applet already computes
   secp256k1 points: `KeyAgreement.ALG_EC_SVDP_DH_PLAIN_XY` initialized with a private key
   carrying the Wei25519 domain parameters (`Ed25519.setCurveParameters`).

2. **Map back to Edwards and compress.** With `u = x_w − A/3` (the Montgomery x-coordinate,
   `A = 486662`), the Edwards coordinates are `ed_x = C·u/y_w` and `ed_y = (u−1)/(u+1)`, where
   `C = sqrt(−(A+2))`. The encoded point is the 32-byte little-endian `ed_y` with the parity of
   `ed_x` in the top bit (`Ed25519.encodePoint`).

3. **Modular arithmetic via keycard-math and one RSA trick.** Additions, subtractions and
   multiplications mod `p = 2^255−19` and mod the group order `L` use `BigNumberMath`
   (`crypto.bigMath`), which itself multiplies via a raw-RSA squaring trick (e=2). The two modular
   **inversions** per point encoding use Fermat's little theorem computed as a *single* raw RSA
   operation: a 256-bit `RSAPublicKey` with modulus `p` and exponent `p−2` behind
   `Cipher.ALG_RSA_NOPAD` (`Ed25519.modInv`). This is the JCMathLib `modExp` mechanism, proven on
   NXP JCOP4 (J3Rxxx) hardware.

All curve constants are embedded in `Ed25519.java` and were generated and verified
programmatically (curve equation, `3·(A/3) ≡ A`, `C² ≡ −(A+2) mod p`); the probe test suite
re-verifies the base point against the curve equation on every run.

## Signing flow (RFC 8032, pure Ed25519, no prehash variant)

`Ed25519.signHash` signs a **32-byte precomputed hash** (for Stellar: the SHA-256 of the
transaction signature payload — computed by the host; the card treats it as the message `M`):

1. Expand the 32-byte secret: `h = SHA-512(secret)`; clamp `h[0..31]` (little-endian) into the
   scalar `s`; `prefix = h[32..63]`. The clamped scalar is reduced mod `L`, which changes neither
   the public key nor signatures but keeps it a valid input for the EC engine.
2. `A = encode(s·B)` — the public key, recomputed per operation (nothing cached across commands).
3. Deterministic nonce `r = SHA-512(prefix ‖ M) mod L` — no on-card randomness is consumed, so a
   weak RNG cannot cause nonce reuse.
4. `R = encode(r·B)`; challenge `k = SHA-512(R ‖ A ‖ M) mod L`.
5. `S = (k·s + r) mod L`; signature is `R ‖ S` (both little-endian per RFC 8032).

`BigNumberMath` state is big-endian; byte order is flipped only at the RFC 8032 boundaries
(`reverse`/`reverseInto`). Signing is fully deterministic: the same key and message always produce
the same signature (asserted in tests).

## Key material and SLIP-0010 derivation

BIP32-style public derivation does not exist for ed25519. SLIP-0010 defines the ed25519 variant:
**hardened-only**, `I = HMAC-SHA512(chain, 0x00 ‖ key ‖ index)`, with the master pair coming from
`HMAC-SHA512("ed25519 seed", seed)`.

- The applet **never persists the raw seed**, so the SLIP-0010 master key + chain code are computed
  at seed-load time (`loadSeed`, reached from both GENERATE KEY and LOAD KEY with a seed) and
  stored in dedicated persistent fields, wiped by REMOVE KEY / FACTORY RESET and whenever a plain
  TLV keypair (no seed) is loaded.
- Derivation happens on-card at SIGN/EXPORT time (`Ed25519.slip10Derive`); paths with any
  non-hardened element are rejected with `SW_DATA_INVALID` (0x6984).
- The Stellar account path per SEP-0005 is `m/44'/148'/n'`; the test suite reproduces SEP-0005
  test vector 1 end-to-end on-card.

## Wire interface

- **SIGN (INS 0xC0), P1 = derive-from-master, P2 = 0x01 (`SIGN_ED25519`)**
  Data: 32-byte hash ‖ derivation path (4-byte big-endian elements, all hardened).
  Response: `A0 81 64 { 80 20 <ed25519 public key>, 88 40 <R ‖ S signature> }`.
  (Same template shape as secp256k1 responses; the pubkey is 32 bytes instead of 65 and the
  signature is the raw 64-byte TLV `0x88` used by the Schnorr path.)
- **EXPORT KEY (INS 0xC2), P2 = 0x03 (`EXPORT_KEY_P2_ED25519_PUBLIC`)**
  Data: derivation path. Response: `A1 { 80 20 <ed25519 public key> }`.
  Only the public key is exportable. Stellar strkey ("G…" address) encoding — version byte,
  CRC16, base32 — is a host-side concern.
- **Cash applet**: holds an independent random-at-install Ed25519 secret (analogous to its
  secp256k1 keypair) and answers SIGN P2=0x01 with the same response template. No PIN or secure
  channel, per the Cash design.

Both applets keep all pre-existing secp256k1/ECDSA/Schnorr behavior and the secure channel
unchanged.

## Platform requirements

- `KeyAgreement.ALG_EC_SVDP_DH_PLAIN_XY` (JavaCard 3.0.5) accepting custom Fp curve parameters.
- Raw RSA (`ALG_RSA_NOPAD`) with a 256-bit public key and arbitrary exponent (`p−2`), operating on
  key-length blocks. This is the JCMathLib assumption for JCOP3/JCOP4-class cards; **verify on
  the target card** — it is the one platform-dependent piece of the design (guarded by dedicated
  regression tests, including inverse results with leading zero bytes).
- SHA-512 (`Crypto.sha512`) and HMAC-SHA512 (native or the existing software fallback).
- `keycard-math` (`BigNumberMath`): `modAdd`/`modSub`/`modMul`/`modRed` with arbitrary moduli.

Memory: one transient work buffer (417 bytes, `CLEAR_ON_DESELECT`) per applet instance, one
transient EC private key, one persistent 256-bit RSA public key, plus 64 persistent bytes for the
SLIP-0010 master in the main applet.

## Simulator support

The bundled jcardsim needed fixes to run any of this (and, independently, the current secure
channel): transient EC private key types, APDU buffer bounds for max-length responses, EC point
on-curve validation, and card-faithful raw `ALG_RSA_NOPAD` (arbitrary-exponent modPow — BC's
RSAEngine block-size rules rejected both the e=2 squaring and the e=p−2 inversion). These live on
the `keycard-sim-fixes` branch of the jcardsim submodule fork. `Ed25519ProbeTest` exercises each
primitive (native XY scalar mult on Wei25519, modMul/modRed mod L, RSA inversion edge cases)
directly against the simulator and cross-checks every result with BigInteger/BouncyCastle.

## Security notes

- Deterministic nonces (RFC 8032) — no RNG dependence during signing.
- The secret expansion, scalars, nonce and all intermediates live in the transient work buffer
  (cleared on deselect); the SLIP-0010 master is persistent by necessity and wiped on key removal.
- Side channels: the native EC engine provides the platform's countermeasures for the scalar
  multiplications (the same ones protecting secp256k1 signing). The `BigNumberMath`-based field
  arithmetic in point *encoding* operates on values derivable from the (public) result point, with
  the exception of the scalar arithmetic `S = k·s + r mod L`, which handles secrets in software —
  the same exposure class as the existing BIP340 Schnorr implementation. A hardened production
  pass should review timing behavior of `BigNumberMath` for secret-dependent branches.
- Invalid inputs: non-hardened SLIP-0010 path elements are rejected; PIN and secure-channel
  requirements for SIGN/EXPORT are identical to the secp256k1 paths.
